**Status: PLAN DO REALIZACJI. Nie rozpoczęto implementacji 0.4.4.**

**Zweryfikowana baza:** `Mentiuszen/ziemianiczyja`, `main`, commit
`a3398c211292e1cd677478ad6c4d456b6d210193` (`v0.4.3`).

> **Dla wykonawcy:** realizować pakiety z §13 kolejno, z regresją przed zmianą oraz

**Cel:** zastąpić obecne przeładowane menu oszczędnym interfejsem gry wojennej,
wprowadzić osobny animowany ekran kampanii i czytelny HUD taktyczny, zachowując
rozgrywkę 0.4.2 oraz pełną lokalizację PL/EN z 0.4.3.

korzysta z lokalnych warstw SVG, minimapa z Canvas 2D, a znaczniki sojuszników

właścicielem czasu i rozgrywki. Nie uruchamiać dodatkowej sceny Babylon dla menu
ani drugiej kamery renderującej świat na minimapę.

**Technologie:** JavaScript ES modules, HTML, CSS, lokalne SVG/obrazy, Canvas 2D,
obecny Babylon.js 8.46.2, Node ≥20, istniejący statyczny build i testy Node;
Playwright wyłącznie jako narzędzie odbioru, nie zależność gry.

**Specyfikacja:** wymagania użytkownika są zebrane w §1; §3–11 doprecyzowują projekt.
Wymiary, czasy animacji, budżety i proponowane interfejsy opisane poniżej są

## 3. Kierunek wizualny i techniczny

### 3.1. Podejście przyjęte

**Modułowy rework istniejącego DOM/CSS + lekka warstwa map i HUD-u.**
Daje nowy wygląd bez wymiany renderera, lokalizacji, magazynu ustawień i pętli gry.
Rozdzielenie `ui.js` jest uzasadnione zakresem zmian, ale nie wolno przy okazji
przepisywać całej aplikacji.

Odrzucone alternatywy:

- Tylko nadpisanie CSS: nie usuwa zależności `controls`, niewłaściwego `back`,
  natychmiastowego startu `continue` i brakujących danych mapy.
- Nowy framework UI albo menu/minimapa jako dodatkowa scena 3D: niepotrzebny wzrost
  zależności, kosztu i ryzyka przy tym zakresie.

### 3.2. Wspólny język wizualny

Tło: przygaszony grafit i ziemiste odcienie, jasna ciepła typografia, jeden akcent
selekcji. Motywy papierowej mapy należą przede wszystkim do kampanii, nie do każdego
przycisku. Nie robić kolejnego interfejsu pełnego obramowanych kart, stempli i etykiet.

Utrzymać jedną hierarchię: tytuł ekranu → interaktywna treść → działania powrotu.
Brak pasków przez całą szerokość, powtarzanego „Front Zachodni / 1916–1918”, napisów
„WEBGL2”, długiej etykiety wersji oraz informacji developerskich w main.

Projektowe wartości początkowe, do oceny na rzeczywistych zrzutach:

| Element | Punkt startowy |
|---|---|
| Margines głównych ekranów | 4–5% szerokości; na małym oknie minimum 20 px |
| Siatka odstępów | 8 / 12 / 16 / 24 / 32 px |
| Tekst przycisku main | 20–26 px przy 1080p, normalna szerokość liter |
| Wiersz ustawienia | minimum 44 px; stałe kolumny etykiety, kontrolki i wartości |
| Podstawowy tekst menu | 15–17 px; opisy pomocnicze 12–14 px, tylko gdy potrzebne |
| Krótka odpowiedź hover/focus | 120–180 ms, bez oczekiwania na końcu animacji |
| Przejście ekranów | 180–250 ms; nie blokuje anulowania ani podwójnie nie uruchamia akcji |
| Czytelność | projektować kontrast co najmniej 4,5:1 dla zwykłego tekstu |

Nie zwiększać `letter-spacing` i nie używać bardzo małego tekstu tylko po to,
żeby pomieścić zbyt wiele informacji. Logo może mieć własną autorską typografię;
reszta korzysta z obecnych/systemowych fontów albo odrębnie zatwierdzonego zestawu
z prawem dystrybucji. Brak zależności od sieciowego serwera fontów.

### 3.3. Responsywność, fokus i ruch

Odbiór desktop: 1280×720, 1366×768, 1920×1080, 2560×1440 i 3440×1440.
Sprawdzić też picker/menu/opcje przy 390×844 i 844×390 oraz powiększeniu tekstu.
To test układu, nie deklaracja obsługi całej gry dotykiem.

Usunąć stałe minima wysokości i marginesy pozostawione po paskach. Main mieści się
bez przewijania przy 1280×720; długie zakładki przewijają **treść**, a nie chowają
nawigację. Na ultrawide nie rozciągać logo ani odstępów między przyciskami do skrajności.

Stany `hover`, `focus-visible`, `active` i `disabled` mają odrębne, czytelne sygnały.
Mysz nie jest jedynym sposobem obsługi. Nie stosować globalnego `outline:none`.
W pickerze prostokątny outline zastępuje własny znacznik opisany w §4.1.

Nieistotny ruch respektuje `prefers-reduced-motion` oraz proponowane ustawienie
`uiAnimations` (domyślnie true). Efektywnie animacje są aktywne tylko wtedy, gdy
ustawienie jest włączone i system nie żąda ograniczenia ruchu. To oddzielny parametr
od istniejącego `motion` sterującego kołysaniem kamery. [W2]

## 4. Ekrany menu

### 4.1. Wybór języka bez ramek

Zachować dwie flagi i ustalony podział USA/UK: USA w górnym lewym trójkącie,
UK w dolnym prawym. Podpisy pozostają `English` i `Polski`. Nie wracać do pytania
USA czy UK ani nie zmieniać samej flagi przy okazji nowego hovera.

**Wygląd neutralny:** sama flaga, pod nią nazwa. Brak ramki wokół obrazu, obrysu
wokół całości, obramowanego podpisu, panelu-karty i wypełnionego prostokąta na hover.
Może pozostać miękki cień pod obrazem, który nie rysuje ostrej krawędzi kafla.

**Hover myszą:** niewielkie uniesienie flagi (do 4 px), powiększenie do około 1,025,
rozjaśnienie i krótka linia **pod nazwą**, nie wokół niej. Hitbox nie porusza się:
transformacja obejmuje zawartość nieruchomego przycisku. Druga flaga nie gaśnie do
nieczytelności i nie zmienia miejsca.

**Fokus klawiatury:** ta sama linia plus mały wskaźnik przed nazwą; rozpoznawalne
również bez koloru i przy wyłączonych animacjach. W trybie wymuszonych kolorów
zachować widoczny systemowy kolor znacznika/tekstu. Nie dodawać z powrotem obrysu
prostokąta przez globalny selektor przycisków.

Cała powierzchnia flagi i podpisu nadal jest jednym semantycznym `button`.
`Tab`, `Shift+Tab`, `Enter`, Spacja działają. Na urządzeniu bez hover wystarczy
jedno dotknięcie; nie stosować schematu „pierwszy tap tylko podświetla”.

Picker nie dostaje górnego/dolnego paska. Nagłówek jest dwujęzyczny i krótki;
pojedyncza pomoc o możliwości późniejszej zmiany języka może pozostać pod wyborem.
Brak sceny, przejęcia kursora i uruchomienia audio. Zachować wszystkie reguły 0.4.3:
brak main przed wyborem, pamięć preferencji, odmowa storage bez blokady, Escape
nie omija wymaganego wyboru.

## 5. Nawigacja i semantyka kampanii

### 5.1. Stany i odpowiedzialności

Zachować istniejący `Application.state` dla głównych stanów. Dodać `campaign`.
Wycofać osobny widok `missions`; funkcję przedsionka `brief` przenieść do wybranej
misji na mapie kampanii. Nie usuwać **odprawy w świecie** ani `PHASE.BRIEFING`.

Stan zakładki to `ui.optionsTab`, nie osobna misja i nie kolejny stan symulacji.
Dopuszczalne: `gameplay`, `controls`, `audio`, `graphics`.

Jawny kontekst powrotu:

- `main → options → main`;
- `campaign → options → campaign`, z tym samym punktem mapy i intencją startu;
- `playing → paused → options → paused`, bez automatycznego wznowienia;
- `campaign → loading → ready → playing`;
- `complete → campaign`, już bez pozostawionej sceny 3D.

Nie ustalać powrotu wyłącznie przez `this.world ? 'paused' : 'main'`.
Wprowadzić mały kontroler nawigacji z ograniczonym kontekstem, nie ogólny framework
routera i nie stos nieograniczenie rosnący przy każdym kliknięciu zakładki.

Priorytet Escape: anulowanie capture klawisza → zamknięcie modala → powrót z opcji
→ wyjście z kampanii do main. W `playing` pauza działa jak obecnie. W pickerze
Escape nie omija wyboru. Obsługa nie może konsumować jednego Escape dwukrotnie.

### 5.2. Dwa przyciski main, różne intencje

**Kontynuuj kampanię:** otwiera mapę kampanii na aktualnej misji, z właściwym
punktem zapisu i poziomem trudności. Dopiero „Wznów misję” uruchamia checkpoint.
Nie odtwarzać za każdym razem pełnego wprowadzenia od Ypres.

**Nowa kampania:** otwiera mapę i wprowadzenie jako **podgląd nowej kampanii**.
W tym demie dostępny start to Cambrai, misja 04. Informację o zakresie demo
pokazać tu, nie na main. Samo wejście, animacja, zmiana trudności i powrót do main
nie kasują checkpointu.

Dopiero „Rozpocznij” uruchamia nową misję. Gdy istnieje aktualny zapis lub ukończony
przebieg, wyświetlić zwięzłe potwierdzenie zastąpienia bieżącej kampanii. Domyślny
fokus na „Anuluj”, nie na działaniu destrukcyjnym. Zachować język i wszystkie opcje.

| Stan danych | Main: Kontynuuj | Ekran kampanii |
|---|---|---|
| Odczyt trwa | Nieaktywny, stan zajętości dostępny dla czytnika | Nie wolno wywnioskować „brak zapisu” przed zakończeniem odczytu |
| Brak danych | Nieaktywny | Nowa kampania dostępna, bez pustego „resume” |
| Poprawny checkpoint | Aktywny | Cambrai, nazwa checkpointu, faktyczna trudność, Wznów misję |
| Ukończony bieżący przebieg | Aktywny | Oznaczenie ukończenia demo, powtórzenie przez świadomy nowy start |
| Uszkodzony checkpoint | Nie uruchamia go | Krótki komunikat, możliwość nowego startu; bez próby `start(null)` pod nazwą „Kontynuuj” |
| Wyłącznie zapis sesyjny | Aktywny w tej sesji | Dyskretna informacja, że nie przetrwa zamknięcia strony |

Kontynuowanie nigdy nie tworzy nowej misji po cichu. Podwójne kliknięcie i
spóźniony odczyt storage nie mogą rozpocząć dwóch światów ani nadpisać nowszej decyzji.

### 5.3. Zapis kampanii bez zmiany snapshotu świata

Mapa nie może zgadywać postępu z tekstu napisu, aktualnej daty komputera ani położenia
punktu SVG. Checkpoint pozostaje autorytatywny dla rozgrywki.

Wprowadzić **mały rekord metadanych przebiegu** w istniejącym object store `saves`,
np. pod kluczem `campaign-progress-v1`. Nie tworzyć drugiej niezależnej bazy zapisu.
Proponowany kontrakt:

```js
// Planowany format metadanych interfejsu; NIE nowy Simulation.snapshot().
{
  version: 1,
  campaignId: 'western-front',
  runId: 'niepusty-identyfikator-przebiegu',
  currentMissionId: 'cambrai',
  status: 'in-progress', // albo 'complete'
  completedMissionIds: [], // tylko rzeczywiście ukończone grywalne misje
  checkpointRef: {
    mission: 'cambrai', missionVersion: 3,
    time: 0, difficulty: 'soldier'
  }
}
```

`runId` pochodzi z aplikacji, nie z `world.random`. `checkpointRef` służy sprawdzeniu
zgodności metadanych; nie jest kryptograficznym dowodem autentyczności zapisu.
Nowy checkpoint i odpowiadające mu metadane zapisywać **jedną transakcją** tego
samego store. Nie opisywać dwóch niezależnych zapisów jako operacji atomowej.
Odczyt pary również odbywa się w jednej transakcji readonly, żeby nie połączyć
checkpointu poprzedniego przebiegu z nowszymi metadanymi.

W produkcyjnych ścieżkach startu, autosave i ukończenia stosować tę samą operację
zapisu pary oraz tę samą kolejkę/generację. Dotychczasowe API `save/load` może
pozostać zgodnym adapterem, ale nie drugim niezależnym mechanizmem, który pomija
aktualizację metadanych. Przy `complete` zachować ostatni prawidłowy checkpoint,
utworzyć opis ukończenia bieżącego `runId` i zapisać spójną parę; `checkpointRef`
odpowiada temu checkpointowi, nie czasowi późniejszej klatki końcowej. Samo ustawienie
starej flagi localStorage nie zastępuje zakończenia nowego rekordu kampanii.

Zachować `SAVE_VERSION=1`, `MISSION_VERSION=3`, klucz ustawień oraz walidację 0.4.2.
Nie wkładać do snapshotu ikon, animacji mapy, timerów pingów ani języka.

Migracja:

1. Poprawny stary checkpoint bez metadanych otrzymuje w pamięci opis przebiegu
   Cambrai zgodny z jego fazą i trudnością; nie odrzucamy go za brak nowego rekordu.
2. Stare `zn-cambrai-complete=1` nie identyfikuje konkretnego przebiegu. Zachować
   jako informację o historycznym ukończeniu, ale nie oznaczać automatycznie każdego
   starego checkpointu jako ukończonej bieżącej kampanii.
3. Snapshot z faktyczną fazą końcową albo spójny nowy rekord ukończenia daje stan
   `complete`. Rekord z nieznanym mission ID/status albo sprzecznym powiązaniem
   nie może aktywować startu innej misji; odbudować bezpieczny opis z poprawnego
   checkpointu i zgłosić błąd metadanych, nie niszcząc checkpointu.
4. Nowy przebieg otrzymuje nowe `runId` i pustą listę ukończeń. Niedostępne Ypres,
   Somma i Flers nie trafiają do tej listy przez obejrzenie wprowadzenia.

Przygotowanie nowej misji odbywa się na kandydacie. Błąd lub anulowanie **przed
zatwierdzeniem zapisu** zachowują poprzednią parę checkpoint/metadane. Zatwierdzona
transakcja jest jawną granicą zmiany przebiegu — nie obiecywać cofnięcia zapisu po
jej zakończeniu. Przed zatwierdzeniem ponownie sprawdzić generację i własność operacji.

Przy odmowie IndexedDB przejście może działać sesyjnie, z jednoznacznym ostrzeżeniem;
obie części pary mają wtedy zgodną kopię w pamięci. Trwały poprzedni zapis nie jest
przedstawiany jako nadpisany, jeśli transakcja się nie powiodła. Nie usuwać danych
przez `localStorage.clear()` ani przez reset wszystkich ustawień.

## 6. Animowana mapa kampanii

### 6.1. Osobny ekran i dwie skale informacji

Mapa zajmuje zasadniczo cały ekran. Jest własnym przedstawieniem frontu zachodniego,
nie screenshotem czy zasobem wyciągniętym z Call of Duty: WWII. Inspiracją jest
**sposób opowiedzenia sytuacji przez mapę, ruch i rozdziały**, nie kopiowanie UI 1:1.

Warstwy obowiązkowe:

1. Podkład geograficzny obejmujący front zachodni od wybrzeża Morza Północnego do
   rejonu granicy szwajcarskiej; czytelna północ, wybrzeże i istotne miejscowości.
2. Datowana linia frontu oraz rozróżnienie stron linią/kreskowaniem i kolorem.
3. Punkty rozdziałów z istniejącego `CAMPAIGN`, z innym stanem dla dostępnych,
   aktualnych, ukończonych i informacyjnych.
4. Linia narracyjnego przejścia Ypres → Cambrai, nieudająca udokumentowanej trasy
   marszu konkretnej jednostki.
5. Obecna pozycja w kampanii oraz lokalny sektor misji po zbliżeniu.
6. Zwięzłe dane wybranego rozdziału i właściwe działania startu/wznowienia.

Warstwa strategiczna mówi **gdzie na froncie jest Cambrai**. Zbliżenie operacyjne
mówi **gdzie zaczyna się grywalna misja i jaki jest cel**. Nie przedstawiać lokalnego
heightfieldu 216×272 m jako mapy całej północnej Francji. Mapa kampanii i minimapa
mają odrębne przestrzenie współrzędnych oraz odrębne źródła geometrii.

W widoku ogólnym użytkownik musi móc zobaczyć cały front; po wejściu fokus przechodzi
na grywalny sektor. Dodać „Cały front” / „Bieżąca misja” i ograniczony zoom.
To działania wewnątrz kampanii, nie nowe pozycje main. Sterowanie kamerą mapy nie
wpływa na mysz ani `yaw/pitch` gracza w świecie.

### 6.2. Dane rozdziałów i granica historii

Zachować istniejące nazwy i kolejność, w obu językach:

| Nr / ID | Stan w tym wydaniu |
|---|---|
| 01 `somme` — Pierwszy gwizdek | Kontekst kampanii, niegrywalne |
| 02 `flers` — Żelazne bestie | Kontekst kampanii, niegrywalne |
| 03 `ypres` — Morze błota | Poprzedni rozdział we wprowadzeniu; niegrywalne |
| 04 `cambrai` — Pęknięta linia | Jedyny grywalny rozdział |
| 05 `amiens` — Ostatnie lato | Zapowiedź kolejnego etapu, niegrywalne |

Punkt informacyjny można wybrać, by odczytać opis, lecz nie może mieć aktywnego
startu. Dostępność treści i jej obejrzenie to różne rzeczy. Używać komunikatu
„Niedostępne w tej wersji”, nie „Ukończono”, gdy gracz danej misji nie rozegrał.

Przykład kierunku narracji PL, do finalnej redakcji i tłumaczenia:

> „Poprzedni rozdział: Morze błota — okolice Ypres, październik 1917.
> Listopad przynosi nowe zadanie pod Cambrai. Tutaj rozpoczyna się dostępna misja.”

Nie dopisywać wyborów gracza, poległych członków oddziału ani wyników poprzedniej
misji, których nie zapisuje gra. Narracyjna obecność poprzedniego rozdziału nie
odblokowuje jego plików i nie staje się warunkiem uruchomienia demo.

**Data bazowa mapy:** 20 listopada 1917, sytuacja przed rozpoczęciem pokazywanego
natarcia. Źródło [H1] rozróżnia atak 20 listopada i niemiecki kontratak 30 listopada.
Nie mieszać tych stanów w jednej rzekomo dokładnej linii frontu i nie nazywać
fikcyjnej końcowej obrony demo rekonstrukcją wydarzeń dziesięć dni później.

`mapSVG()` z 0.4.3 nie dostarcza zweryfikowanej polilinii całego frontu. Przed
finalnym eksportem wykonać zadanie kartograficzne: wskazać datę, arkusze, zakres,
źródła i punkty kontrolne; zapisać je w `docs/UI_ART.md` i manifeście mapy.
[H2] potwierdza istnienie arkusza Villers-Guislain z liniami poprawionymi do
20.11.1917, ale sam rekord katalogowy **nie daje współrzędnych całego frontu**.
W tej analizie nie wykonano digitalizacji historycznej linii.

Własna generalizacja jest dopuszczalna, z dyskretnym opisem „Schemat sytuacji”
w kampanii/legendzie. Nie udawać dokładności mapy sztabowej ani brać współczesnych
granic administracyjnych za granice frontu. Informacje historyczne i fabularne
rozdzielić tak samo jak w dotychczasowej dokumentacji gry.

### 6.3. Sekwencja animowana

Proponowany przebieg wejścia **Nowa kampania**, łącznie około 6–8 sekund:

| Czas orientacyjny | Obraz i informacja |
|---|---|
| 0–0,6 s | Wejście całego frontu i legendy stron |
| 0,6–2 s | Zbliżenie/akcent na Ypres i jednozdaniowe przypomnienie poprzedniego rozdziału |
| 2–4 s | Rysowanie przerywanej trasy przeniesienia uwagi w stronę Cambrai |
| 4–5,5 s | Przesunięcie i zoom do Cambrai, pokazanie daty 20 listopada |
| 5,5–7 s | Zarys natarcia, pojawienie się bieżącej pozycji oraz panelu dostępnej misji |
| Stan końcowy | Stabilna, obsługiwalna mapa; bez odtwarzania sekwencji w pętli |

Animacja obejmuje rzeczywisty ruch mapy, linię trasy, stany znaczników i przejścia
napisów — nie tylko fade całego obrazka. Tekstu nie wypalać w PNG. Po stronie EN
kolejność i czas pozostają te same; dłuższa lokalizacja mieści się w zaplanowanych polach.

Przycisk „Pomiń” jest dostępny od początku. Pominięcie ustawia **dokładnie ten sam
stan końcowy**, usuwa stare callbacki i nie uruchamia misji. Przy ograniczonym ruchu
pokazać końcową mapę bez panningu, zachowując treść w zwięzłym podsumowaniu.

Przy „Kontynuuj”, po powrocie z opcji oraz po ukończeniu demo nie odtwarzać całego
wprowadzenia. Kamera wraca do bieżącego punktu, najwyżej z krótkim przejściem.
Odświeżenie PL/EN nie resetuje pozycji mapy, wybranego rozdziału ani osi czasu.

Ukończenie demo może zmienić **lokalny znacznik postępu/zdobycia celu**. Nie przesuwa
całej historycznej linii frontu o kilometry na podstawie samego `director.phase`.
Zapowiedziany kierunek natarcia odróżnić od stanu faktycznie osiągniętego.

### 6.4. Technika i czas życia

Mapa: własne lokalne SVG i dane `src/data/campaign-map.js`; jedno spójne mapowanie
geografii do `viewBox`. Aktualną misję wiązać z `CAMPAIGN.id`, nie z indeksem obrazka.
Warstwy i podpisy mają identyfikatory, tekst pochodzi z i18n.

Animacjami zarządza `CampaignScreen`: ma `mount`, `update`, `setReducedMotion`,
`unmount`; jego instancja posiada listę aktywnych animacji i callbacków. Opuszczenie
ekranu, przerwanie, zmiana języka i błąd zasobu nie mogą „wskrzeszać” starej sekwencji.

`performance.now()` służy menu; `world.time` służy rozgrywce. Animacja kampanii nie
wywołuje `Simulation.tick`, nie konsumuje RNG ani nie zapisuje ukończenia rozdziału.
Po zakończeniu sekwencji mapa jest event-driven; nie przelicza całej treści w każdej
klatce. Nie pobiera kafli mapowych, fontów ani danych frontu z zewnętrznego API.

## 7. Opcje — cztery uporządkowane kategorie

### 7.1. Układ i zawartość

Na górze treści ekranu: **Rozgrywka · Sterowanie · Dźwięk · Grafika**.
EN: **Gameplay · Controls · Audio · Graphics**.
Poniżej znajduje się wyłącznie aktywna kategoria. Zakładki są nawigacją tego
widoku, nie powrotem do usuniętego ozdobnego topbara.

| Kategoria | Kontrolki / istniejące klucze |
|---|---|
| Rozgrywka | Język `language`; trudność nowej kampanii `difficulty`; napisy `subtitles`; kołysanie kamery `motion`; efekty obrażeń `damageEffects` |
| Rozgrywka — nowe elementy tego wydania | Minimapę `showMinimap=true`; znaczniki sojuszników `showAllyMarkers=true`; animacje menu `uiAnimations=true` |
| Sterowanie | Czułość `sensitivity`; wszystkie przypisania `DEFAULT_KEYS`; istniejące stałe przyciski myszy i Esc/F3 jako czytelne wiersze informacyjne |
| Dźwięk | Głośność główna `master`, efekty `effects`, otoczenie `ambient` |
| Grafika | Jakość `quality`; limit FPS `maxFps`; skala renderowania `renderScale`; pole widzenia `fov`; liczniki `showFps`, `showCpu`, `showGpu` w zwartej grupie „Statystyki” |

Nie dodawać martwych suwaków muzyki, dialogów, RT czy synchronizacji, których
backend nie realizuje. Nie rozbijać obecnego audio przy okazji przeniesienia jego
trzech suwaków. Nie usuwać pod spodem istniejącego mechanizmu odczytu CPU/GPU.

Wartości i zakresy wspólnego schematu:

- `maxFps`: liczba całkowita 0–360; `0` wyświetlane jako „Bez limitu” / „Unlimited”.
- `renderScale`: 0,5–1,5, krok 0,05; ujednolicenie z obecnym walidatorem, bez
  cichego obcięcia zapisanych 1,30–1,50 do starego limitu kontrolki 1,25.
- `fov`: 60–105°, krok 1; `sensitivity`: 0,2–3, krok 0,05.
- Istniejące poziomy głośności i intensywności: 0–1, krok 0,05.
- Nowe przełączniki są boolowskie; starsze ustawienia otrzymują powyższe wartości
  domyślne. Nie dopisywać obiektu UI do snapshotu misji.

Na ekranie opcji nie pokazujemy tablic mnożników obrażeń ani wykładu o VSync,
cache, WebGL i timer queries. Opcje nadal muszą robić dokładnie to, co opisuje
etykieta. Trudność w trakcie trwającej/wczytanej misji **nie zmienia jej profilu**:
kontrolkę nazwać „Trudność nowej kampanii”, a faktyczny poziom rozgrywanej misji
pozostaje w podsumowaniu kampanii/pauzy. TTL pingów korzysta z poziomu świata,
nie z przygotowanego wyboru dla kolejnego startu.

### 7.2. Usuwamy ścianę tekstu, nie informację o błędzie

Zwykły wiersz ma etykietę, kontrolkę i wartość. Jednowierszowa pomoc pojawia się
wyłącznie tam, gdzie bez niej ustawienie byłoby mylące, np. przy wartości 0 FPS
lub braku obsługi pomiaru GPU. Można użyć wspólnego pola pomocy dla aktywnego wiersza;
nie otwierać jednocześnie kilkunastu tooltipów ani nie wymagać hovera do odczytu błędu.

Informacja o odmowie zapisu, niepoprawnym klawiszu czy nieudanej zmianie grafiki
pozostaje widoczna kontekstowo i przetłumaczona. Nie przenosić błędów tylko do konsoli.
Dokładne wyjaśnienia techniczne pozostają w README/znanych ograniczeniach.

### 7.3. Zachowanie i obsługa

Zmiany działają na bieżąco. Nie pokazywać fikcyjnego „Zastosuj”, jeśli wszystko już
zostało zapisane. Wystarczy „Wróć” i „Przywróć tę kategorię”. Reset wymaga
potwierdzenia i nie resetuje innych kategorii; reset Rozgrywki zachowuje język.
Reset Sterowania obejmuje przypisania i czułość, nie grafikę ani checkpoint.

Przełączanie zakładki nie zapisuje ponownie całego świata, nie uruchamia audio,
nie przywraca klawiszy domyślnych i nie powoduje `go('playing')`. Otwieranie z pauzy
pozostawia symulację zatrzymaną. Zmiana języka zachowuje aktywną kategorię,
przewinięcie, sensowny fokus i wartości kontrolek.

Przy zmianie języka, zakładki, zamknięciu opcji i resecie zakończyć capture klawisza.
Escape podczas capture oznacza tylko anulowanie przypisania. Konflikt przypisania
zachowuje dotychczasową świadomą politykę zamiany klawiszy i jest pokryty regresją.
Nie wiązać ważności capture z nieistniejącym już stanem aplikacji `controls`.

Zakładki implementują `tablist`, `tab`, `tabpanel`, `aria-selected` i powiązania
etykiet. Strzałki lewo/prawo oraz Home/End przełączają kategorię bez zauważalnego
opóźnienia; Tab przechodzi do jej kontrolek. Stosować wzorzec [W1], nie nadawać
roli tab zwykłemu nagłówkowi bez obsługi klawiatury.

Suwaki nie odtwarzają całego DOM przy każdym `input`. Aktualizować wartość i
właściwy subsystem; droższe `view.applySettings` skonsolidować do nie więcej niż
jednego wywołania na klatkę. Odświeżenie grafiki zatrzymanej sceny nie tyka symulacji.
Jedno źródło schematu ustawień ma zasilać walidację i widok, bez dwóch rozjeżdżających
się tabel zakresów.

## 8. Układ HUD-u w grze

### 8.1. Strefy ekranu

| Obszar | Docelowa treść |
|---|---|
| Prawy górny | Zwarty moduł minimapy, **z lokacją i datą wewnątrz modułu** |
| Bezpośrednio pod minimapą | Bieżący cel, zwięzła podpowiedź i istniejący postęp obrony |
| Lewy dolny | Obecne zdrowie, regeneracja, wytrzymałość i postawa |
| Prawy dolny | Obecne liczby amunicji, granaty, reload; w miejscu nazwy broni ikona |
| Góra–środek | Istniejący kompas, bez powielania daty i nazwy misji |
| Środek | Celownik, sygnalizacja trafień, interakcje i pilne ostrzeżenia |
| Dół–środek | Napisy; niepodparte przez mapę, flagi i nowe panele |
| Lewy górny | Opcjonalne FPS/CPU/GPU; diagnostyka F3 poniżej, bez zajmowania minimapy |

Prawy górny moduł ma początkowo 220–280 px szerokości przy 1080p. U góry w jego
obrębie znajduje się wąski obszar metadanych, niżej **kwadratowe pole mapy**.
To jeden moduł, nie powrót do nagłówka przez cały ekran. Przy 720p pole mapy może
mieć 180–210 px, ale tekst pozostaje czytelny. Pod nim odstęp 8–12 px i cele.

Miejscowość i data nie są wpisane ręcznie do drugiego miejsca w HUD. Używać tych
samych deskryptorów bieżącej misji w PL/EN. W Cambrai pozostaje data tej misji;
czas komputera ani długość sesji nie przesuwają kalendarza wojny.

Usunąć stare `.hud-chapter` w prawym rogu i stary lewy `.hud-goal` po migracji;
nie zostawiać ukrytych duplikatów aktualizowanych co 50 ms. Gdy minimapa zostaje
wyłączona, zachować lokację/datę oraz cel w zwartej prawej kolumnie, bez pustego
prostokąta po mapie.

W obrębie prawej kolumny cel ma pierwszeństwo nad pomocniczym opisem. Długi PL/EN
może łamać się na kolejne wiersze; nie ucinać tytułu celu przez `line-clamp`.
Dopasować rozmiar minimapy do wysokości okna, zanim zacznie zasłaniać amunicję.

Checkpoint/toast przenieść do osobnego miejsca **u góry–środka, poniżej kompasu**.
Wspólna kolejka prezentacji zajmuje najwyżej dwa krótkie wiersze i nie nakłada się
na prawą kolumnę. Nie zachowywać stałego `top:166px` po dawnym HUD ani pokazywać
równocześnie dwóch komunikatów o tym samym checkpointcie. W niskim oknie ograniczyć
szerokość komunikatu do wolnej środkowej strefy, zamiast przenosić go na minimapę.

Usunąć stały drobny napis HUD „ESC / F3 / WERSJA”. Pomoc należy do Sterowania,
a numer do main/diagnostyki. Nie zmienia to skrótów Esc/F3 ani ich działania.

### 8.2. Ikony broni zamiast nazw

Zachować pozycję i proporcje liczb `mag`/`reserve`, zachowanie reloadu, pustego
magazynka, cyklu zamka i granatów. Zmienić **wyłącznie wizualny identyfikator broni**.

Dostarczyć osobne czytelne sylwetki: SMLE, Gewehr 98, Webley, Lewis oraz MG 08
(dla kompletności rejestru `WEAPONS`, nawet jeśli obecnie nie jest bronią gracza).
Nie używać jednego ogólnego karabinu dla wszystkich. Wspólny kierunek lufy,
kolor jasny, przezroczystość tła i wyrównanie optyczne; Webley nie może wyglądać jak
maleńka kropka z powodu kopiowania szerokości karabinu. Punkt startowy: pole 150–180×40–48 px.

Rejestr ikon jest indeksowany przez `weapon.id`. Podmieniać `src`/symbol tylko przy
zmianie broni, nie tworzyć obrazu co tick. Nazwa pozostaje w danych oraz jako tekst
dostępności (`aria-label`/tekst ukryty wizualnie). Nie przywracać dużej nazwy obok
ikony. Brak ikonki to czytelny neutralny symbol i błąd diagnostyczny; test wydania
wymaga pokrycia wszystkich aktualnych ID.

Pliki SVG nie potrzebują osadzonego fontu, nie zawierają zewnętrznych odnośników
ani kopiowanych ikon CoD. Wygląd zatwierdzić na jasnym niebie, błocie i przy silnej
winiecie obrażeń, a nie tylko na jednolitym tle edytora.

## 9. Minimapę budujemy z danych gry, nie z obrazka menu

### 9.1. Domyślna prezentacja

**Proponowana wersja bazowa:** północ na górze, mapa nie obraca się; gracz jest
strzałką obracającą się według `player.yaw`. Widoczny obszar jest wycentrowany na
graczu, po ±60 m w osiach X/Z, czyli kwadrat 120×120 m. Te wymiary są punktem
startowym planu do lokalnej oceny, nie zmianą wymiarów świata.

Ta sama skala i geometria na wszystkich trudnościach oraz jakościach. Trudność
zmienia czas ujawnienia strzelców, nie fizyczną mapę i nie liczbę sojuszników.
W 0.4.4 nie potrzeba drugiego trybu obrotu, kilku poziomów zoomu HUD czy interaktywnej
mapy otwieranej klawiszem — osobne menu kampanii ma inną funkcję.

Tło: czytelny schemat terenu, okopów, ramp, dróg, budynków i ważnych przeszkód.
Nie rysować każdego źdźbła, billboardu i wizualnego LOD. Dodać aktualny cel jako
mały symbol odróżniający się kształtem od jednostek; gdy jest poza polem, pojedynczy
wskaźnik celu na krawędzi, bez doklejania poza kadrem ukrytych przeciwników.

### 9.2. Współrzędne i źródło tła

Źródła: `src/data/world-map.js`, `TRENCHES`, `RAMPS`, `roadX`, `Terrain` i rzeczywiste
obiekty `layout/collision.boxes`. Dynamiczne przełamania drutu uwzględniają
`destroyedObstacles` i zdarzenie `breach`. Nie tworzyć ręcznej listy murów tylko dla
minimapy. Tło nie zależy od Low/Ultra, widocznego LOD ani aktywności siatek renderera.

Dla kwadratowego pola o boku `S`, środka gracza `(px,pz)` i zasięgu osiowego `R`:

```text
screenX = S/2 + (worldX - px) * S/(2R)
screenY = S/2 - (worldZ - pz) * S/(2R)
headingX = sin(playerYaw)
headingY = -cos(playerYaw)
```

Dodatnie Z jest północą w przyjętej konwencji kompasu gry. Nie odwracać znaku przez
intuicyjne przeniesienie współrzędnych canvas. Przy krawędzi świata zachować gracza
w środku, a obszar poza mapą wypełnić neutralnie; nie rozciągać pozostałego fragmentu.

`S` i pozycje warstwy HTML są w CSS px. Bufor Canvas skaluje się według
`devicePixelRatio` (proponowany limit 2). `renderScale` sceny 3D nie zmienia pozycji
punktów w CSS. Zoom przeglądarki i zmiana rozmiaru ponownie konfigurują bufor oraz
transformację; nie nakładać `scale(dpr,dpr)` wielokrotnie bez resetu macierzy.

Tło wygenerować raz przy utworzeniu świata albo z danych przygotowanych offline;
po zmianie istotnej geometrii unieważnić odpowiednią warstwę. Nie generować
heightmapy w każdej klatce i nie uruchamiać `nav.path()` do rysowania mapy.

### 9.3. Sojusznicy i bieżący cel

Na mapie pokazywać aktywne jednostki o frakcji gracza:

- żywą piechotę — małe jasne/oliwkowe znaczniki;
- istniejące niezniszczone czołgi — inny kształt; unieruchomienie może mieć wariant
  symbolu, ale nie wskrzesza pojazdu;
- aktywny sojuszniczy samolot znajdujący się nad widocznym obszarem — lekki symbol
  samolotu, bez znacznika dla przyszłego zaplanowanego wylotu.

Filtr wynika z frakcji i faktycznego stanu świata, nie z prefixu `uk-` ani języka UI.
Nie pokazywać jednostek jeszcze nieaktywnych, trupów ani przyszłych spawnów.
Sojusznicy mogą być widoczni na minimapie za osłoną; ich flagi w świecie mają
odrębną politykę widoczności (§10).

Przy skupieniu znaczników zachować priorytet gracza i celu. Nie przesuwać ikon tak
daleko, żeby sugerowały inną stronę ściany; ewentualne rozróżnienie robić obrysem,
kształtem i kolejnością rysowania. Nie dodawać nazw każdej jednostki na stałe.

### 9.4. Ujawnianie strzelających wrogów

| Rzeczywista trudność świata | Czas od ostatniego wystrzału |
|---|---:|
| Rekrut / Recruit | 3,0 s |
| Żołnierz / Soldier | 2,0 s |
| Weteran / Veteran | 1,0 s |

To proponowane doprecyzowanie wskazanego przez użytkownika przedziału 1–3 s.
Zdefiniować je w jednym miejscu, np. `src/data/hud.js`, bez zmiany mnożników obrażeń.

**Kontrakt obowiązkowy:**

1. Ping powstaje z rzeczywiście wyemitowanego strzału, także gdy wróg strzela do
   sojusznika, nie tylko do gracza. Naciśnięcie spustu bez amunicji, reload, sam stan
   AI `aim`, impact i dźwięk nie są strzałem.
2. Źródła podstawowe: `shot` broni ręcznej i pokładowej. Dla `cannon` dodać jawne
   `faction` w emiterach działa/czołgu i normalizować `pos` do tego samego kontraktu.
   Wystrzał wrogiego działa również ujawnia jego pozycję na wskazany czas.
   Sam wybuch granatu, bomba i przelot samolotu nie tworzą kropki strzelca.
3. Pozycja pingu to **kopia pozycji wylotu w chwili wystrzału**, nie żywe
   `npc.pos` ani referencja do przesuwanego wektora. Po strzale przeciwnik może odejść,
   lecz znacznik pozostaje w miejscu oddania strzału do kolejnego wystrzału/wygaśnięcia.
4. Jeden aktywny ping na `owner`. Następny strzał tego właściciela aktualizuje pozycję
   i `expiresAt = event.time + duration`. Nie tworzyć 20 kropek dla jednej serii MG.
5. Ujawnienie ma zasięg pola minimapy **w chwili strzału**: przy ±60 m akceptować
   `max(abs(dx),abs(dz)) <= 60`. Poza nim nie dodawać pingu ani wskaźnika na krawędzi.
   Stary daleki wystrzał nie ujawnia się dopiero po dobiegnięciu gracza.
6. W obrębie tego zasięgu **nie wymagamy LOS** — to świadomy sygnał oddania strzału,
   nie system wykrywania wzrokiem ani fizyczny model słyszalności. Nie dokładać
   raycasta i symulacji propagacji dźwięku dla każdej kropki.
7. Nie ujawniać cichych wrogów, wszystkich członków ich oddziału, celu AI ani drogi.
   Renderer minimapy dostaje gotową listę kontaktów; nie filtruje sam pełnej listy
   wrogów i nie może przypadkiem odrysować ich bieżących pozycji.
8. Usunięcie lub śmierć strzelca nie stanowią dodatkowej wiadomości dla gracza:
   ping może dożyć swojego TTL w ostatniej pozycji. Nie przerabiać go w darmowe
   potwierdzenie zabicia przeciwnika za ścianą.
9. Wszystkie terminy są liczone w **czasie symulacji**. Pauza, opcje i ukryta karta
   nie zużywają TTL. Ograniczenie FPS, niski preset i zmiana PL/EN nie przedłużają go.
10. Load/restart/nowy świat zerują kontakty i nadają nową generację sesji.
    Nie odtwarzać pingów z `shotTime` NPC ani z dawnych zdarzeń snapshotu. Zmiana języka,
    powrót z opcji i wyłączenie/włączenie samego widoku minimapy nie zerują kontaktów.

Końcowe 20–25% czasu może płynnie wygaszać kropkę; przy reduced motion wystarczy
stały symbol z usunięciem w terminie. Nie migotać. Kontakt logicznie wygasa przy
`now >= expiresAt`. Canvas usuwa symbol przy pierwszym zaplanowanym odrysowaniu
minimapy po tym terminie: zwykle do 1/30 s później, a przy niższym FPS w najbliższej
dostępnej klatce. Nie obiecywać dokładności jednej klatki 165 Hz przy odrysowaniu
mapy 30 Hz; test modelu sprawdza dokładny termin, test obrazu jawny interwał odrysowania.

`world.noises` ma inną rolę i krótki własny TTL. Nie przedłużać jego żywotności
na potrzeby minimapy, bo zmieniłoby to percepcję AI.

### 9.5. Dane, dystrybucja i koszt

`Application.events()` nadal pobiera batch raz. `UI.event` przekazuje odpowiednie
zdarzenia do `TacticalContacts`; audio i efekty zachowują swój dotychczasowy batch.
`TacticalContacts` jest modelem prezentacji przypisanym do konkretnego świata.
Nie jest globalnym singletonem pamiętającym poprzednią misję.

Normalizacja do planowanego formatu:

```js
// Utworzone z shot/cannon; nie zapisuje się w checkpointach.
{
  owner: 'de-4', faction: 'de',
  pos: { x: 12, y: 1.5, z: 40 },
  time: 25.5
}
```

Walidować typ właściciela, frakcję, skończone liczby pozycji i czasu oraz bieżącą
generację. Starszy event nie zastępuje nowszego pingu. Duplikat nie odnawia TTL
według czasu odbioru. Limit początkowy 128 właścicieli; po wygaśnięciu usuwać wpisy,
a przy przepełnieniu usuwać najwcześniej wygasający i zwiększać licznik diagnostyczny.
Nie tworzyć nieograniczonej historii wszystkich strzałów.

Canvas aktualizuje ruchome symbole do 30 razy/s; logiczna rejestracja strzałów
odbywa się podczas dystrybucji każdego kroku, niezależnie od renderu. HUD-owe teksty
mogą nadal mieć wolniejsze odświeżanie. Nie wykonywać reflow dla każdej kropki.
Po wyłączeniu minimapy nie rysować canvas, ale zachować poprawnie starzejący się
lekki model kontaktów. Przywrócenie widoku pokazuje tylko jeszcze ważne informacje.

## 10. Flagi nad sojusznikami

### 10.1. Wygląd i znaczenie

Mała półprzezroczysta flaga nad głową, inspirowana czytelnością oznaczeń CoD2.
Dla aktualnej brytyjskiej piechoty jest to **samodzielna flaga UK** — nie hybryda
USA/UK użyta do wyboru języka. Wybranie polskiego interfejsu nie zmienia frakcji
na polską ani symboli jednostek.

Propozycja startowa: 24–32 px szerokości, krycie około 0,45–0,60, bez karty z imieniem,
ramki dookoła i jaskrawego billboardu. Delikatny cień zwiększa czytelność na niebie.
Dystans maksymalny początkowo 60 m; wielkość ekranowa ograniczona, by bliski sojusznik
nie zasłaniał widoku wielką flagą. Tylko żywa piechota, bez własnej flagi gracza.

Nazwa, HP, ranga i dystans nad każdym NPC nie są w zakresie. Czołgi i samoloty mają
symbole minimapy, nie wymagają flag zawieszonych nad kadłubem.

### 10.2. Kotwiczenie i widoczność

Kotwica bierze głowę z obecnego `hitSpheres(actor)` (`part:'head'`), z małym pionowym
marginesem około 0,20–0,25 m. Dzięki temu uwzględnia stanie, kucanie i przesunięcie
głowy leżącej postaci. Nie dokładać na sztywno 1,9 m do stóp i nie przeczesywać całego
szkieletu po nazwach kości w każdej klatce. Przyszłe modele 0.5 mogą dostarczyć
lepszą kotwicę przez ten sam adapter.

Projektować punkt **rzeczywistą macierzą kamery** z bieżącej klatki `GameView`,
uwzględniając pitch, FOV, ADS i poprawioną orientację. Sam test przed/za graczem
z `player.yaw` obecnego `marker()` nie wystarcza dla całej przestrzeni.
Sprawdzać kamerę, przestrzeń clip/depth i położenie w oknie; nie wyświetlać
odwróconych punktów zza kamery przy krawędzi ekranu.

Proponowana polityka: flagi w świecie nie prześwietlają ścian i terenu. Widoczność
sprawdza geometrię do głowy, z użyciem istniejącej kolizji, bez zmiany reguł AI.
LOS do sprawdzenia kierować do głowy, nie do flagi ponad dachem; inaczej symbol
może zdradzać niewidocznego człowieka w schronie.

Najpierw filtr frustum/dystansu, dopiero potem LOS. Budżet początkowy: maksymalnie
4 sprawdzenia LOS na renderowaną klatkę, kolejka rotacyjna, cache do 0,15 s czasu
symulacji. Nieprzetestowany/przeterminowany kandydat pozostaje ukryty; nie zakładać
widoczności przy braku wyniku. Ruch dynamicznej osłony, load i duża zmiana pozycji
kamery unieważniają odpowiednie cache. Dopuszczalna zwłoka starego wyniku wynosi
najwyżej zadeklarowane 0,15 s, nie kilka sekund.

Na celowniku, napisach i panelu celu nie układać stosu flag. Zarezerwowane obszary
HUD-u wyciszają flagę, nie przesuwają jej nad inną postać. Nie dodawać znaczników
wrogom ani strzałek poza ekranem. Minimapę i flagi oceniać oddzielnie: widoczny na
mapie sojusznik za murem nie musi mieć flagi w widoku 3D.

### 10.3. Technika

Lekki pool elementów HTML/SVG z `pointer-events:none`, poza kolejnością Tab.
Tylko transformacja i krycie zmieniają się przy aktualizacji. Pool może rosnąć do
liczby kandydatów w obecnej misji, z limitem bezpieczeństwa 64 i diagnostyką;
nie tworzyć/usunąć DOM dla każdej postaci w każdej klatce.

Projektowanie pozycji wykonać **po** synchronizacji i renderze właściwej kamery,
przed końcową prezentacją HUD-u. Wspólny adapter podaje CSS px w prostokącie canvas;
nie mieszać pikseli bufora renderowania z pozycją stałego overlay.

Nie zmieniać `scene.activeCamera` dla flag, nie uruchamiać drugiej kamery, nie
wywoływać `scene.render()` dodatkowo. Flagi nie są pickable i nie przejmują strzału,
PPM, kółka, Pointer Lock ani zdarzeń opcji.

Na pause/dead/loading/complete ukryć je wraz z HUD-em. Po loadzie zbudować powiązania
z nowymi obiektami NPC; ID z poprzedniej sceny nie zachowuje starego węzła/projekcji.
`disposeMission` i `UI.dispose` zwalniają pool oraz wszystkie obserwatory.

## 11. Lokalizacja, dostępność i ochrona poprzednich wersji

**PL i EN są równorzędnym zakresem wydania**, nie zadaniem „po redesignie”.
Nowe katalogi muszą obejmować: cztery działania main, zakładki, opisy kampanii,
sekwencję Ypres/Cambrai, legendę mapy, stany zapisu, potwierdzenia, błędy metadanych,
nowe ustawienia, etykiety minimapy i teksty dostępności ikon.

Zachować `message(key,params)` oraz istniejące `t/text/translate`. Bez kopii
`main-pl.js`/`main-en.js`, wykrywania języka po treści, string-replace całego HTML
czy tłumaczenia DOM po renderze. Nazwy własne broni i miejsc mogą zostać niezmienne;
zdania i etykiety nie.

Tekst nie jest wypalony w ilustracji ani mapie SVG jako krzywe. Wyjątkiem jest
niezmienny logotyp nazwy własnej. Parametry klawiszy, czasu i checkpointów są
interpolowane oraz escapowane jak w 0.4.3. Nie wprowadzać `innerHTML` z nazwy
checkpointu lub danych z localStorage bez bezpiecznego formatowania.

Zmiana języka:

- nie zmienia czasu świata, RNG, pozycji, HP, amunicji, trudności ani stanu misji;
- nie resetuje minimapy, TTL, historii bieżących kontaktów i aktywnego komunikatu;
- nie powtarza sekwencji mapy ani dźwięku i nie przedłuża timera napisów;
- zachowuje zakładkę i sensowny fokus, anuluje tylko nieaktualny capture;
- nadal przełącza lokalizowaną teksturę mapy na stole odprawy;
- zachowuje poprawne językowe linki do historii, licencji i ograniczeń.

Po nowym podziale modułów dopasować `tools/check-localization.mjs`. Nie usuwać
kontroli kompletności ani whitelistować całego nowego katalogu, żeby test przeszedł.
Usunięte teksty main można wycofać z katalogów po sprawdzeniu wszystkich konsumentów;
historyczne raporty i dokumenty nie muszą być przepisywane na nowy design.

Flagi dekoracyjne i ikony mają puste `alt` wtedy, gdy etykietę zapewnia przycisk;
ikona broni ma dostępną nazwę. Tytuł celu jest tekstem DOM, nie wyłącznie rysunkiem
na canvas. Błędy i wynik zapisu pozostają komunikowane dostępnie. Na brakujące
grafiki reagować sensowną strukturą ekranu, nie pustą czarną stroną.

### 12.3. Kontrakty interfejsów do realizacji

```text
buildCampaignViewModel({checkpointState, checkpoint, progress,
                       intent='continue', selectedMissionId='cambrai',
                       newDifficultyId='soldier'})
  -> {canContinue, missionId, mode, checkpointLabel, difficultyId, completedIds}
  checkpointState: 'loading' | 'none' | 'ready' | 'invalid'
  intent: 'new' | 'continue'
  mode: 'new' | 'resume' | 'complete' | 'unavailable'
  canContinue opisuje zwalidowany istniejący przebieg, niezależnie od podglądu nowego.
  mode wynika z dostępności selectedMissionId, intencji i stanu danych; loading
  pozostawia działania startu nieaktywne. Nowy start bierze newDifficultyId, resume
  profil checkpointu. missionId jest ID wybranego rozdziału, nie jego numerem.
  Funkcja czysta: bez zapisu, ładowania świata i tłumaczenia na stały język.

CampaignScreen.mount(host, viewModel, context)
CampaignScreen.update(viewModel, context)
CampaignScreen.setReducedMotion(enabled)
CampaignScreen.unmount()
  context: {language, intent:'new'|'continue', onAction, reducedMotion}
  update zmienia tekst/stan, nie odtwarza automatycznie wprowadzenia.

Store.loadCampaign()
  -> Promise<{checkpoint, progress, checkpointState, legacyCompleted}>
Store.saveCampaign(checkpoint, progress, {isCurrent})
  -> Promise<boolean>  // true: zatwierdzony trwały zapis; false: niezatwierdzony
  W tej samej kolejce i transakcji co stare save; caller oddziela anulowanie
  od odmowy storage przez isCurrent/status operacji, nie przez zgadywanie.

TacticalContacts({sessionId, maxContacts=128})
TacticalContacts.recordShot(event, context) -> boolean
  event: {owner, faction, pos:{x,y,z}, time}
  context: {sessionId, playerFaction, playerPos:{x,y,z}, difficultyId}
TacticalContacts.sample(now) -> Array<{owner,pos,shotAt,expiresAt,opacity}>
TacticalContacts.reset(sessionId)
  sample zwraca kopie/read-only wartości, usuwa wygasłe; nie czyta NPC.

worldToMinimap(point, center, size, range) -> {x,y,inside}
  point/center: {x,z}; size: CSS px; range: półrozmiar obszaru w metrach.

projectToHud(point, camera, viewportCss) -> {x,y,visible,depth}
  point: {x,y,z}; viewportCss: {left,top,width,height} względem overlay.
  Wykorzystuje macierz faktycznej kamery, nie sam yaw gracza.
```

Fasada UI zachowuje publiczne `event(e)`; do ledgeru dodaje kontekst aktualnego
świata. Bez nowego konsumenta `consumeEvents()`. Ledger otrzymuje nową `sessionId`
przy zaakceptowaniu nowego `world`, nie przy każdym `render()` lub zmianie języka.

## 13. Kolejność wykonania — pakiety dla agenta

Zależności główne: **P0 → P1 → P2**; następnie P3 oraz P4; **P4 → P5**;
**P1 → P6 → P7**; P8 korzysta z układu P7; P9 integruje wszystkie ekrany;

wynik możliwy do sprawdzenia. Akceptacja wyglądu nie zastępuje testu zachowania,
a zielony test logiki nie zatwierdza grafiki.

### 14.2. Przykłady testów czystej logiki

Poniższe fragmenty określają oczekiwany kontrakt i są materiałem dla wykonawcy.
**Nie zostały uruchomione; moduły 0.4.4 jeszcze nie istnieją.** Po dodaniu testów
sprawdzić ich rzeczywistą porażkę przed implementacją, a potem wynik całego zestawu.

`tests/v044-contacts.test.mjs`:

```js
import test from 'node:test';
import assert from 'node:assert/strict';
import { TacticalContacts } from '../src/ui/hud/tactical-contacts.js';

const ctx = difficultyId => ({
  sessionId: 1, playerFaction: 'uk',
  playerPos: { x: 0, y: 0, z: 0 }, difficultyId,
});
const shot = (time, x = 10) => ({
  owner: 'de-4', faction: 'de', pos: { x, y: 1.5, z: 20 }, time,
});

for (const [difficulty, ttl] of [['recruit', 3], ['soldier', 2], ['veteran', 1]]) {
  test(`reveal expires in simulation time: ${difficulty}`, () => {
    const contacts = new TacticalContacts({ sessionId: 1 });
    contacts.recordShot(shot(10), ctx(difficulty));
    assert.equal(contacts.sample(10 + ttl - 0.001).length, 1);
    assert.equal(contacts.sample(10 + ttl).length, 0);
  });
}

test('ping copies the muzzle position; it is not a live actor tracker', () => {
  const contacts = new TacticalContacts({ sessionId: 1 });
  const event = shot(10);
  contacts.recordShot(event, ctx('soldier'));
  event.pos.x = 55;
  assert.equal(contacts.sample(10.2)[0].pos.x, 10);
  const returned = contacts.sample(10.2);
  // A consumer must not be able to corrupt the retained point.
  try { returned[0].pos.x = -40; } catch {}
  assert.equal(contacts.sample(10.3)[0].pos.x, 10);
});

test('same shooter refreshes one point; older events cannot roll it back', () => {
  const contacts = new TacticalContacts({ sessionId: 1 });
  contacts.recordShot(shot(10), ctx('soldier'));
  contacts.recordShot(shot(11, 20), ctx('soldier'));
  contacts.recordShot(shot(10.5, 5), ctx('soldier'));
  const current = contacts.sample(12.9);
  assert.equal(current.length, 1);
  assert.equal(current[0].pos.x, 20);
  assert.equal(current[0].expiresAt, 13);
  assert.equal(contacts.sample(13).length, 0);
});

test('same world time is a pause, not an opportunity to expire the ping', () => {
  const contacts = new TacticalContacts({ sessionId: 1 });
  contacts.recordShot(shot(10), ctx('veteran'));
  for (let frame = 0; frame < 1800; frame++) {
    assert.equal(contacts.sample(10.5).length, 1);
  }
  assert.equal(contacts.sample(11).length, 0);
});

test('session reset rejects old-world events and does not resurrect shotTime', () => {
  const contacts = new TacticalContacts({ sessionId: 1 });
  contacts.recordShot(shot(10), ctx('recruit'));
  contacts.reset(2);
  contacts.recordShot(shot(10.1), ctx('recruit'));
  assert.equal(contacts.sample(10.2).length, 0);
});

test('friendly and out-of-range shots create no enemy contact', () => {
  const contacts = new TacticalContacts({ sessionId: 1 });
  contacts.recordShot({ ...shot(10), faction: 'uk' }, ctx('soldier'));
  contacts.recordShot(shot(10, 60.01), ctx('soldier'));
  assert.equal(contacts.sample(10.1).length, 0);
});
```

import test from 'node:test';
import assert from 'node:assert/strict';
import { worldToMinimap } from '../src/ui/hud/projection.js';

test('north is +Z, east is +X, and the player stays in the centre', () => {

Rekord arkusza Ordnance Survey z liniami poprawionymi do 20.11.1917. Potwierdza

**H3 — The National Archives, „Trench map with detailed key”, WO 297/6648.**
Pomocniczy przykład języka map i legendy. Arkusz dotyczy Sommy, aktualizacja
8 kwietnia 1916 — **nie używać go jako stanu Cambrai z listopada 1917**.
`https://www.nationalarchives.gov.uk/education/resources/medicine-on-the-western-front-part-two/trench-map-with-detailed-key/`

**W1 — W3C WAI-ARIA Authoring Practices, Tabs Pattern.**
Role, powiązania i klawiaturowa obsługa zakładek. Przykłady wymagają dostosowania
i testów w docelowych przeglądarkach; nie są automatycznym potwierdzeniem dostępności.
`https://www.w3.org/WAI/ARIA/apg/patterns/tabs/`

**W2 — MDN, `prefers-reduced-motion`.**
Odczyt preferencji ograniczenia nieistotnych animacji. Nie używać eksperymentalnego
PreferenceManager jako wymagania gry; wystarcza CSS media query i `matchMedia`.
`https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/prefers-reduced-motion`

Nie analizowano kodu Call of Duty ani nie odtwarzano jego ukrytych parametrów.
Flagi, kompozycja mapy i sposób narracji są wymaganiami/inspiracją podanymi przez
użytkownika; liczby TTL, rozmiary, animacje i budżety są własnym projektem 0.4.4.

**Stan końcowy tej pracy:** dostarczony plan, bez zmian kodu gry, zasobów, branchy,
changelogu działającego wydania i publikacji. Implementacja i jej odbiór są przyszłymi
etapami opisanymi powyżej.
